# Content Factory: мультимодальный видео-аудитор для анализа и рекомендаций по доработке генеративного видео

> **Статус проекта:** Домашнее задание №1 (Бизнес-анализ) / Финальный проект программы MFDP (дедлайн: 9 декабря).

---

## 1. Business Understanding (Бизнес-анализ)

### 1.1. Организационная структура и коммуникация

* **Заказчик / Продуктовая роль:** Автор проекта выступает в роли самостоятельного создателя контент-производства (Self-Producer / Creator), формирующего требования к качеству автоматизированной генерации.
* **Разработчик (ML Engineer):** Автор проекта (проектирование архитектуры, сбор данных, настройка разметки, ручная верификация тестового эталона, QLoRA-обучение VLM и оценка метрик).
* **Пользователи:** Создатели контента, маркетологи и e-commerce бренды, использующие AI-генерацию для регулярного производства видеороликов.
* **Эксперты / Асессоры:** Автор проекта выполняет ручную верификацию эталонного Gold Test Set.
* **Коммуникация:** Итеративная разработка, консультации с менторами курса и защита результатов 9 декабря.

### 1.2. Бизнес-цель, модель, данные и существующие решения

* **Бизнес-цель проекта:** Автоматизация контроля качества готовых AI-видеороликов и подготовки рекомендаций по их исправлению. Создание специализированного автономного ML-сервиса (**Video Auditor**), который принимает готовый видеоклип и текстовый сценарий (промпт), анализирует их на предмет визуальных артефактов и сценарных несоответствий с привязкой ко времени, а затем выдаёт структурированный JSON-отчёт с рекомендациями для последующей доработки.
* **Выбор модели и бэкап:** В качестве основного кандидата рассматривается **Qwen3-VL-8B** (благодаря нативной поддержке привязки текста к таймкодам). В качестве резервного кандидата рассматривается **Qwen2.5-VL-7B** на случай возможных ограничений или несовместимости библиотек видео-QLoRA для новой архитектуры (требует предварительной проверки). Окончательный выбор подтверждается по итогам раннего Smoke Test.
* **Существующие решения и отличие от них:**
  1. *Ручной отсмотр контента человеком:* Требует ориентировочно 1,5–2 минуты ручного анализа на один ролик (предварительная оценка, которая будет уточнена замерами), что критически не масштабируется при потоковой генерации.
  2. *Готовые модели-оценщики (например, VideoScore и VideoScore2 на базе Qwen2.5-VL-7B):* Существующие бенчмарки выдают общие скалярные оценки качества ролика по шкале (1–5), но не локализуют дефекты во времени и не генерируют структурированные JSON-инструкции для исправления сценарных ошибок. Наше решение специализировано именно на пошаговой диагностике.
* **Ресурсы, хранение и лицензии:**
  * *Вычислительные ресурсы:* Облачные GPU (RunPod / Colab Pro) для проведения Smoke Test, QLoRA-дообучения и инференса.
  * *Данные и хранение:* Открытые датасеты сгенерированных роликов, публичные бенчмарки (`VideoFeedback`, `VideoScore2`) и синтетические инъекции; версионирование данных через `DVC`.
  * *Лицензии:* Open-source модель `Qwen3-VL-8B` (при условии подтверждения свободной лицензии), открытый стек PyTorch / Hugging Face.
  * *План проверки бюджета:* Контроль лимитов токенов teacher-API при авторазметке и оптимизация времени аренды GPU.

### 1.3. Стратегия данных и защита от утечек

* **Объём и сплит данных:**
  * Формируется общая выборка с разделением на тренировочную (`train`), валидационную (`val`) и тестовую (`test`) части. Группировка связанных видео выполняется строго по исходным проектам и промптам (разные генерации одного сценария не попадают одновременно в обучение и тест), что снижает риск утечек данных. На `val`-выборке проводятся подбор гиперпараметров и выбор модели.
  * *Gold Test Set (60–80 роликов):* Ручная проверка автором проекта, эталонные метки и таймкоды для расчёта основных метрик (Recall, F1, FPR). Доверительные интервалы метрик будут рассчитаны на этом ручном эталоне с учётом ограничений небольшого размера выборки.
  * *Расширенный набор (200–300 роликов):* Автоматическая разметка несколькими API для дополнительного исследования. Результаты FPR на нём считаются предварительными из-за возможных ошибок консенсуса teacher-моделей.
* **Пайплайн разметки и синтетические инъекции:**
  * Авторазметка `train` через Gemini API.
  * *Генерация таймкодов для синтетики:* Временные интервалы (`start_sec`, `end_sec`) для синтетических сценарных инъекций задаются программно в момент инъекции (детерминированный эталон для Temporal IoU). Типы инъекций, исходные видео и близкие дубликаты строго разделяются между `train` и `test`.

### 1.4. Риски проекта и план их минимизации

1. **Риск не уложиться в сроки:** Жёсткое ограничение скоупа (только визуальный анализ коротких клипов без звука) и резервный день перед защитой.
2. **Смещение учителя (Teacher Bias):** Использование гибридного подхода — автоматическая разметка дополняется ручным Gold Test Set для независимой итоговой оценки.
3. **Технические ограничения VRAM / несовместимость библиотек:** Проведение раннего Smoke Test для проверки поддержки QLoRA для видео в выбранной модели и готовность задействовать резервного кандидата (`Qwen2.5-VL-7B`).

### 1.5. Решаемые задачи с точки зрения аналитики (Data Mining goals)

* **Постановка задачи в технических терминах:** Мультимодальная классификация и временная локализация сценарных/визуальных несоответствий по видеоряду и текстовому промпту.
* **Вход:** Видеоклип (семплированный с привязкой ко времени) и текстовый сценарий (промпт).
* **Выход:** Валидный JSON-отчёт с классификацией проблем, временными интервалами (`start_sec`, `end_sec`) и рекомендациями по корректировке (пример формата):

```json
{
  "video_id": "sample_001",
  "has_error": true,
  "issues": [
    {
      "start_sec": 3.2,
      "end_sec": 4.8,
      "error_type": "object_consistency",
      "description": "The character's bag disappears between frames.",
      "correction_instruction": "Keep the bag visible throughout the shot."
    }
  ]
}
```

* **Метрики и критерии успешности:**
  * **Recall ≥ 0.80** — предварительная цель по обнаружению дефектных роликов (минимизация пропущенного брака). Выполнение проверяется строго в паре с контролем FPR.
  * **F1-score** — баланс Precision и Recall, сравнивается с baseline.
  * **FPR ≤ 15%** — предварительная цель по доле чистых роликов, ошибочно признанных дефектными.
  * **Temporal IoU** — качество локализации дефектов во времени (порог фиксируется после базовой модели).
  * **JSON Validity Rate ≥ 98%** — предварительная цель по структурной корректности отчётов.
* **Критерий успешности (проверяемые гипотезы):** Дообученная модель должна показать статистически значимый прирост ключевых метрик относительно базовой модели (Zero-Shot) — данное утверждение является проверяемой гипотезой для предстоящих экспериментов, а не обязательным обещанием. Сравнение с коммерческими API и экономия ресурсов также оцениваются экспериментально.

### 1.6. План проекта (Project Plan по фазам и неделям)

Общая продолжительность — 4 недели (с учётом защитного буфера до 9 декабря):

1. **Фаза 1: Business Understanding (13 ноября):** Фиксация скоупа, требований и структуры JSON-отчёта. **Результат:** готовый `README.md`.
2. **Фаза 2: Data Understanding & Smoke Test (13–15 ноября):** Ранний Smoke Test (проверка загрузки Qwen3-VL-8B, GPU-памяти и совместимости с QLoRA; оценка резервного кандидата Qwen2.5-VL-7B), сбор пула видеогенераций (включая модели Kling/Seedance) и загрузка бенчмарков. **Результат:** подтверждение технической осуществимости.
3. **Фаза 3: Data Preparation (16–22 ноября):** Авторазметка train, генерация непересекающихся синтетических инъекций, ручная разметка Gold Test Set (60–80 роликов с интервалами) и формирование расширенного набора (200–300 роликов) через API-консенсус. **Результат:** готовые датасеты в DVC.
4. **Фаза 4: Modeling (23–29 ноября):** Замер базовой Zero-Shot модели и полноценное QLoRA-дообучение. **Результат:** обученные веса LoRA.
5. **Фаза 5: Evaluation (30 ноября – 3 декабря):** Прогон экспериментов, расчёт метрик (Recall, F1, FPR, Temporal IoU с расчётом доверительных интервалов), анализ результатов. **Результат:** сводная таблица результатов.
6. **Фаза 6: Deployment & Defense Prep (4–8 декабря):** Упаковка модуля в инференс-скрипт, оформление репозитория. Запас 1 день (9 декабря — защита). **Результат:** готовый проект к защите.
